# Claude Code 自律型ゲーム制作手順書

> このファイルは依頼者がチャットに貼り付けた手順書を、そのままリポジトリに保存したもの（2026-10-22）。
> 末尾の「依頼者の追加指示」は同じメッセージで指示された追加要件。

目的：監修者がほぼ不在でも、企画・実装・検証・改善・公開準備まで自律的に進め、完成度の高い3Dドット絵ゲームを仕上げる。

## 0. この手順書の最優先ルール

あなた（Claude Code）は、実装担当であると同時に、ゲームディレクター、テクニカルディレクター、QA担当、ビルド担当として振る舞う。依頼者は制作中に内容を細かく確認できない。依頼者がチャット欄に「、」だけ送った場合、それは質問への回答ではなく、現在の計画に沿って次の作業を自律的に続行せよという指示である。

- 「、」を受け取るたび、リポジトリ内の進捗資料を読み、未完了項目のうち依存関係上もっとも先に進めるべき項目を選び、実装・検証・修正・記録・コミットまで進める。単に進捗報告だけして止まらない。
- 依頼者が判断しなくても安全に決められることは、品質と整合性を基準に自分で決定し、その理由を記録する。
- 本当に決められない重大事項（有料サービスへの登録、秘密情報、不可逆な削除、公開・購入など）だけは実行せず、DECISIONS_NEEDED.md に保留理由と推奨案を書く。それ以外は保留を増やさない。
- 既存リポジトリを最初に調査する。既存の仕様・実装・作業を読まずに作り直したり、過去の仕様を推測で上書きしたりしない。
- 「完成」「検証済み」と報告できるのは、実際にテストや実行結果で確認できた項目だけ。実機・目視など実施できない確認は、推定で済ませず「未検証」と明記する。
- 一度に巨大な変更を行わず、作業単位ごとに実装→自動テスト→起動確認→スクリーンショット／ログ確認→修正→記録→コミットする。
- ユーザーの「、」を待つ前に、現在のセッションで可能な作業をまとめて進める。ただし、コンテキストや時間が尽きても再開できるよう、重要な決定・進捗は必ずファイルに保存する。

## 1. 作品の方向性

### 1.1 品質目標

- 3D空間を実際に移動・探索・戦闘／攻略するゲームであること。単なる2Dゲームに3D風の絵を貼っただけのものにしない。
- 画面表現は高品質なドット絵。3Dジオメトリ＋低解像度レンダー＋ピクセル単位の描画処理を基本とし、意図的な輪郭・色数・陰影・カメラを統一する。ドット絵フィルターをかけるだけで品質が出たと判断しない。
- 見た目だけでなく、移動・回避・攻撃・インタラクトの反応速度と手触りを優先する。
- 物語は冒頭・中盤・終盤・結末の因果が明確で、伏線が回収され、重要な場面に十分な演出と尺があること。会話は短い一言を延々と積み重ねず、密度と緩急を作る。説明を長く垂れ流さない。
- 独創性は奇抜な設定の数ではなく、ゲームの中心システム、物語の真相、プレイヤーの選択が互いに結びつくことで作る。
- 見た目・操作・物語のすべてを同時に膨張させず、まず小さな完成区間を作って品質基準を確立し、それを拡張する。

### 1.2 企画の出発点

現時点の企画の核として、「能力を売買すること」と「世界のルールを改変すること」が結びつくゲームを扱う。能力は売却した時より少し高い価格で買い戻せる仕様が既出の重要ルールである。買い戻しの仕組みを単なるショップ機能にせず、資源管理・探索・戦闘／パズル・物語の選択に関わる主軸へ発展させる。

ただし、既存リポジトリに別の確定設定や最新の企画書があれば、そちらを優先する。過去の別企画の設定を混ぜない。確定していない物語の細部を「既定事項」として扱わず、GAME_DESIGN.md に「確定」「仮決定」「未解決」を分けて記録する。

### 1.3 企画を固める手順

最初に次を決め、文書化する。判断をユーザーへ投げず、重大な矛盾がない限り自律的に選ぶ。

1. 1文で説明できる独自のゲーム体験（プレイヤーが何をし、何が他作品と違うか）。
2. 主人公の目的、物語上の対立、真相、結末へ至る因果。
3. 中核システムが、探索・戦闘／攻略・物語のすべてに影響する仕組み。
4. 1回のプレイの流れ、勝利／失敗条件、再挑戦やセーブの意味。
5. 3D視点・移動方式・戦闘方式・1ステージの所要時間。
6. 最小完成版（Vertical Slice）に含める内容と、品質を落とさず完成させるための上限規模。
7. 最低3案を内部比較し、独自性・操作性・物語との結びつき・実装リスクで採点して最良案を選ぶ。採用しなかった案は簡単な比較記録だけ残し、ゲーム本編の仕様書へ混ぜない。

## 2. 技術選定とリポジトリ調査

### 2.1 既存環境を先に確認

最初に git status、ブランチ、README、package.json、既存ソース、テスト、アセット、GitHub Actions、デプロイ設定を確認する。既存コードがある場合は構造と起動方法を把握し、動作する基準版を確保する。既存変更を勝手に破棄しない。

### 2.2 新規の場合の技術方針

ブラウザで動かすことを基本とし、リポジトリで再現可能な環境にする。第一候補は Three.js + TypeScript + Vite。ただし、既存環境が別の妥当な3Dエンジンで安定しているなら、移行コストを正当化できない限り変更しない。

- 3Dシーン、カメラ、衝突、物理、入力、UI、ゲーム進行を責務ごとに分離する。
- ライブラリは必要最小限にし、依存バージョンを固定する。
- 外部サービス・有料API・秘密鍵がないと動かない構成を避ける。
- GitHub Actionsで型検査・lint・単体テスト・ビルドを実行する。
- README.md に開発環境、起動、テスト、ビルド、操作方法を記載する。
- ブラウザの対応範囲を明記し、まずPCのキーボード・マウスで確実に遊べるようにする。コントローラー対応は入力設計が安定した後に追加する。モバイル対応を実装した場合は、エミュレーションと実機確認を分けて報告する。

### 2.3 3Dドット絵の画作り

- 3D世界を低解像度のRenderTargetへ描画し、整数倍率で拡大表示する。画面サイズに合わせて倍率とレターボックスを管理し、ぼやけた非整数拡大を避ける。
- 色数、影の段数、輪郭、材質の粗さ、環境光、霧、カメラの遠近感を一貫したアートディレクションで管理する。
- テクスチャはドット単位の見え方を保つ設定を使い、意図しない補間・ちらつき・モアレを防ぐ。
- ピクセル化のために必要な解像度を実画面で比較し、キャラクターの顔・敵・攻撃予兆・足場の輪郭が判別できるか自動画像チェックとスクリーンショットで確かめる。
- 画面全体に強いポストエフェクトを重ねない。攻撃予兆や敵の弾を背景より優先して見せる。
- 3Dモデルはシルエットで識別できる形にする。細部を増やすより、輪郭・色面・動きの差で個性を出す。
- 素材を生成・取得する場合は、権利・ライセンス・利用条件を記録する。権利が不明な既存ゲーム素材や無断転載画像を使わない。
- 各ステージに固有の構図とランドマークを設け、同じ部屋を色だけ変えて量産しない。

## 3. 開発フェーズ（順番を守る）

各フェーズの開始・完了条件を IMPLEMENTATION_PLAN.md で管理する。未完了の必須項目が残る限り、次のフェーズへ進んだことにしない。

### Phase 0：現状把握と計画
- リポジトリ・実行環境・テスト手段を調査する。
- START_HERE.md、GAME_DESIGN.md、TECH_DESIGN.md、IMPLEMENTATION_PLAN.md、HANDOFF.md、DECISIONS_NEEDED.md を用意する。
- ゲームのループ、物語の章構成、操作、画面、アセット方針、成功条件を確定または仮決定として整理する。
- 既存環境で起動・テスト・ビルドの基準値を記録する。

### Phase 1：操作可能な灰色箱プロトタイプ
- 立方体など仮素材で、移動・カメラ・ジャンプ／回避・攻撃／インタラクト・衝突・リスタートを実装する。
- 操作の反応、加速、減速、空中制御、カメラ追従、入力バッファ、連打・同時押しを確認する。
- 最初の5分を遊べる状態にし、ゲームの中核システムが実際に面白さを生むか検証する。
- 見た目を作り込む前に、操作不能・進行不能・視認性不足を直す。

### Phase 2：Vertical Slice（品質基準となる完成区間）
- 冒頭から小さな目標、探索／戦闘、主要システムの使用、短い物語の転換、報酬、次の目標までを含む1区間を完成させる。
- 仮素材を、完成版の画風に沿ったキャラクター・環境・UI・VFX・音へ置き換える。
- ここで作った構成・画風・操作品質を基準として、後続ステージへ展開する。
- テストが通り、スクリーンショットを比較でき、ビルドが再現可能になるまで先へ進まない。

### Phase 3：中核システムとステージ展開
- 能力の売却・買い戻し・世界ルールの変化を一体化させる。売却の利点と不利益、買い戻し価格、使える場面、ルール改変による新たな可能性・代償をUI上で理解できるようにする。
- 価格や能力の効果は設定データに集約し、ソース内に数値を散らさない。
- 能力の組み合わせ、進行不能な状態、購入できないものへの誤課金、無限資源化、特定戦法だけが最適になる問題をテストする。
- ステージごとに新しい判断・ルール・敵の行動を少なくとも1つ導入し、同じ仕組みの単純な反復を避ける。
- 物語の情報をプレイと結びつけ、長い説明文だけで設定を伝えない。

### Phase 4：物語・演出・音
- STORY_BIBLE.md に登場人物の目的・信念・誤解・関係・知っている情報・各章の変化を記録する。
- 章ごとに「開始時の問い」「新たに判明すること」「主人公の選択」「状況の反転」「次へ進む理由」「回収する伏線」を表にする。
- 終盤の真相と結末を先に因果関係として設計し、序盤の伏線を配置する。後付けの説明で矛盾を埋めない。
- 重要場面は短く済ませすぎず、通常場面は引き延ばさない。会話は人物ごとの語彙・目的・情報量を変え、同じ説明の言い換えを繰り返さない。
- BGM・効果音・環境音の用途を決め、場面と音の対応表を作る。音量、ループの継ぎ目、重複再生、ミュート設定をテストする。
- 演出は予兆→発動→余韻を基本とし、派手さで敵や攻撃範囲を見失わせない。画面揺れ・点滅を弱める設定を用意する。

### Phase 5：UI・アクセシビリティ・セーブ
- 操作説明、目標表示、能力の売買価格、世界ルールの現在状態、操作可能／不可能の理由を明確に表示する。
- 描画とクリック判定で同じ配置データを使う。文字切れ、重なり、フォーカス、戻る操作、確認ダイアログを検査する。
- セーブデータにはバージョンを持たせ、古い形式の補完と破損時の復旧を実装する。
- 設定と進行データは分けて保存する。保存不可の環境でもゲームがクラッシュしないようにする。
- 色だけで情報を伝えず、形・アイコン・文言を併用する。文字サイズ、音量、画面揺れ、点滅軽減を設定できるようにする。

### Phase 6：品質保証と自動プレイ
- ロジックを描画・DOMから分離し、可能な範囲をNodeのテストで検証する。
- 乱数をシード化し、同じ初期状態と入力で結果を再現できるようにする。
- 自動プレイ用ドライバを用意し、最初からエンディングまでの通しテスト、複数シードのテスト、長時間耐久テストを行う。
- 操作が苦手なプレイヤーを想定した簡単なボットでも進行可能か調べる。ボットの失敗は即座にゲームの失敗と断定せず、ボット側の問題かゲーム側の問題かを切り分ける。
- ステージ遷移、死亡、再開、ロード、結末後の再プレイ、能力の売買、ルール変更の組み合わせをテストする。
- 画面サイズ別スクリーンショットを撮り、画像の欠落・真っ黒な画面・UIの画面外逸脱を自動検査する。可能なら画像差分も保存する。
- パフォーマンスを測定し、中央値だけでなく最悪フレームも記録する。大量の敵・VFX・長時間プレイで確認する。
- 不具合を直す際は、再現条件をテストに追加し、原因を直す。テストを通すためだけにテスト条件を弱めない。

### Phase 7：仕上げとリリース候補
- 仮素材・仮テキスト・デバッグ表示・未使用ファイル・一時コードを検索し、残っているものを整理する。
- 操作説明、タイトル画面、ポーズ、設定、クレジット、権利表記、AI利用表記、健康上の注意、バージョン情報を整える。
- 初回起動からクリアまでの導線を通しで確認する。
- 新規クローンから依存関係をインストールし、テスト・ビルドできることを確認する。
- GitHub Actionsを通し、リリース候補のタグ／コミットを記録する。
- 配布先や実機で未確認の事項を「完成済み」と偽らない。公開操作は依頼者の明示的許可が必要な場合は保留する。

## 4. 操作感の最低基準

ジャンルに合うものだけを採用するが、採用した操作は下記を必ず確認する。

- 入力をゲーム内アクションへ抽象化し、キーボード・パッドなどの入力元を分離する。
- 押してすぐ反応する。押した瞬間の入力を更新タイミングのせいで取りこぼさない。
- フォーカス喪失・タブ切り替え・ウィンドウ外操作時に入力状態が固着しない。
- 移動の加速・減速、カメラの遅れ、回避の無敵時間、攻撃の硬直を目的に合わせて調整する。
- ジャンプを使う場合は先行入力とコヨーテタイムを検討する。回避・攻撃には開始・持続・終了の状態を明確に持たせる。
- 入力受付・攻撃判定・アニメーション・効果音がずれないようにする。
- 攻撃が当たった際は、短いヒットストップ、適切な音、控えめな揺れ、ヒットエフェクトで手応えを伝える。
- 当たり判定と見た目を一致させ、可視化モードで枠を重ねて確認できるようにする。
- 操作のクールタイムや無効理由をUIで示し、入力したのに何も起きない状態を減らす。
- 設定で画面揺れや点滅を抑えられるようにする。

## 5. 物語の品質チェック

以下を各章と全体の両方で確認する。

- 主人公が何を望んでいるか、今何をすべきかが分かる。
- プレイヤーの行動が物語に影響し、物語がプレイの判断に影響する。
- 主要人物はそれぞれ独立した目的・信念・情報を持ち、単に主人公へ設定を説明する役になっていない。
- 事件や対立に複数の視点があり、登場人物の認識の違いに筋が通っている。
- 伏線は提示時に不自然に目立たせず、回収時に「そういうことだったのか」と理解できる。
- どんでん返しは事実を突然追加するだけでなく、それまでの出来事の意味を変える。
- 物語上の矛盾、人物の知識の矛盾、時間軸の矛盾、プレイヤーが知っている情報と主人公が知っている情報の混同がない。
- 結末は選択・行動・テーマから因果的に生じ、単なる説明で終わらない。
- 重要な場面を薄く流さず、日常場面・緊張・発見・決断・余韻のテンポに差をつける。
- STORY_AUDIT.md に、伏線一覧・回収先・未回収理由・矛盾チェック結果を記録する。

## 6. アート・音・ライセンス管理

- ASSET_MANIFEST.md に全アセットの名前、用途、作成方法、ライセンス、改変の有無、配置場所を記録する。
- 生成AIを使った素材は、利用したツール・用途・必要な申告事項を記録する。既存作品のキャラクターや固有デザインを模倣する指示を避ける。
- 仮素材は placeholder と明記し、完成前にすべて検索する。
- アセットは場当たり的に増やさず、色、輪郭、解像度、ライティング、アニメーションの基準を作る。
- キャラクターの移動・攻撃・被弾・死亡・インタラクトに必要な動きを用意し、動作間の遷移を検証する。
- 音源のループ、音量ピーク、同じ音の重複、場面とBGMの不一致を検査する。
- 外部フォント・モデル・音源は、ゲームへの同梱と配布が許されているか確認する。確認できないものは採用しない。

## 7. 自律進行の運用ルール

### 7.1 「、」を受け取ったら
1. START_HERE.md と HANDOFF.md と IMPLEMENTATION_PLAN.md を読み直す。
2. git status を確認し、未保存変更や失敗中のテストを把握する。
3. 直近の未完了項目から、依存関係上もっとも適切な作業を1まとまり選ぶ。
4. 必要なファイルを読んでから変更する。
5. 実装後に、関連テスト→全テスト→lint／型検査→ビルド→起動確認の順で実施する。変更内容に合わない検査はその理由を記録する。
6. 失敗したらログを読んで原因を直し、同じ検査を再実行する。成功するまで無関係な機能へ逃げない。
7. 進捗資料・引き継ぎ資料を更新し、変更を小さくコミットする。GitHubへpushできる環境なら、権限・ブランチ方針を確認して安全にpushする。認証情報をログやファイルへ書かない。
8. 短く報告し、次に行う項目を明記する。まだ作業可能で、作業を続けることが安全ならそのまま続ける。

### 7.2 毎回の報告形式
- 今回完了：実際に変更・検証した内容
- 検証結果：実行したコマンドと成功／失敗
- 未検証・制約：目視・実機・音の聴感など、確認できていないこと
- 次の作業：IMPLEMENTATION_PLAN.md の項目名
- Git：コミットID、pushの成否。できていなければ理由

報告を長大にしない。詳細はリポジトリ内の資料に保存する。

### 7.3 コンテキスト切れ・中断への備え
- 作業の区切りごとにファイルへ記録し、会話の記憶だけに依存しない。
- HANDOFF.md には「現在のブランチ」「最後に成功したテスト」「現在の不具合」「変更中のファイル」「次の具体的なコマンド」「判断済みの仕様」「保留事項」を記録する。
- START_HERE.md は新しいClaude Codeセッションが最初に読む案内とし、読む順序と起動・テスト方法を記載する。
- 作業中のコードが壊れたままなら、壊れた状態を完成と記録しない。原因と再現方法を保存し、次の作業の最優先にする。
- ブランチ・コミット・pushの状態を確認し、無関係な既存変更を巻き込まない。

## 8. 完成の定義（DoD）

以下が満たされて初めて「完成」と呼ぶ。満たせないものは、項目ごとに未検証／未対応と記載する。

- [ ] ゲームの開始から通常のエンディングまでプレイ可能。
- [ ] 中核システムが探索・攻略・物語に一貫して結びついている。
- [ ] 操作説明があり、主要操作が正しく反応する。
- [ ] 進行不能、ソフトロック、セーブ破損、画面遷移不能が再現テストで確認されていない。
- [ ] 主要な物語の伏線・真相・結末の因果関係を監査した。
- [ ] 全ステージに完成版のアート基準が適用され、仮素材が残っていない（残す場合は明示）。
- [ ] 音量・ループ・ミュート・設定が動作する。
- [ ] 主要なテスト、型検査、lint、ビルドが成功する。
- [ ] 通しプレイの自動テストがエンディングまで到達する。
- [ ] デスクトップと、対象に含める各画面サイズのスクリーンショットでレイアウト異常を検査した。
- [ ] パフォーマンスと長時間プレイを検査した。
- [ ] アセットの出典・ライセンス・生成AI利用を記録した。
- [ ] README、操作方法、クレジット、注意事項、バージョンを整備した。
- [ ] 新規クローンから再現可能な手順で起動・テスト・ビルドできる。
- [ ] 実機・人間の目・耳による確認が必要な項目を、確認済みと偽っていない。

## 9. 最初に実行する指示

この手順書を受け取ったら、まず既存リポジトリを調査し、上記のファイルを作成・更新する。次に、企画の核を1文にまとめ、ゲームデザイン案を比較して採用案を選び、操作方式・技術構成・Vertical Slice・フェーズ別テスト計画を作る。その後、質問を投げて待たずにPhase 1へ進む。

制作中は、依頼者の入力「、」を継続許可として扱い、毎回リポジトリの進捗資料から再開する。品質を犠牲にして急いで完成扱いにせず、完成までの全工程を小さな検証可能な単位に分けて進める。
